# 后续接入真实 API

当前工程默认禁止外部生成。配置页面中的 URL 与模型 ID 都是占位值，只写入本机，不构成真实连接。请勿把 API key 粘贴进网页、JSON 配置、聊天、代码或 Git 仓库。

## 本次创作流程：趋势参考 → 角色成片 → 发布文案

趋势选题每天保留 1–2 条，目标为 K-pop 与虚拟偶像各一条；主题、男生／女生素材分区、动作类型和变装类型分别保存。先播放原片，记录动作、转场时点、构图与可见的妆容／服装变化。没有观看或观察不足时保留未知，不从标题猜测需要几张造型图。

用户已确认使用 **OpenRouter 的 Seedance**，版本保留可切换；发布目标为 **TikTok 美国市场，英文文案与 hashtags**。TikTok／抖音分享链接是网页链接，不能当作视频文件地址直接传入。下列两种能力需要分别确认：

- **手势舞／舞蹈**：供应商支持参考视频动作迁移时，使用有权传给该供应商的动作视频文件或媒体直链，搭配自有角色照片。只有图生视频能力时，可以用拆解出的动作提示词创作相似玩法，但不能承诺精准跟随参考视频的节拍和手指动作。
- **变装／变妆**：先用固定角色参考图分别生成前造型和后造型，保持脸、发型基准、画幅、背景和构图一致；确认这两张图后，再调用支持首尾帧或多图参考的视频接口。只有单图输入的接口，需分别生成两段后剪辑转场；“有两张图”本身不代表该 API 能同时接收或完成指定变装。

真正提交时由后端读取密钥、上传所需媒体、保存供应商任务 ID、查询完成状态并取回成片。页面展示“等待造型图／等待生成／生成中／待审核／失败”的实际状态。当前仍是接入设计，没有真实调用；妆前妆后照片也需要单独的图像生成／编辑模型，Seedance 视频接口不会自动替代这一步。

### OpenRouter 的实际调用边界

截至 2026-11-15，官方页面列出 [Seedance 2.0](https://openrouter.ai/bytedance/seedance-2.0) 和 [Seedance 2.5](https://openrouter.ai/bytedance/seedance-2.5)。接入时使用可配置的模型 ID，不自动从一个版本切换到另一个付费版本。先调用 `GET https://openrouter.ai/api/v1/videos/models`，按所选模型的实际能力校验时长、分辨率、画幅、首尾帧和参考素材支持，再允许提交。

[OpenRouter 视频 API 文档](https://openrouter.ai/docs/guides/overview/multimodal/video-generation) 的调用顺序是 `POST /api/v1/videos` → 保存返回的任务 ID → `GET /api/v1/videos/{jobId}` 查询 → 完成后由后端读取 `/api/v1/videos/{jobId}/content` 并保存 MP4。查询暂时失败时继续查询同一个任务，避免重新提交重复花费。公开网页不能放需要 Authorization 的下载地址作为可直接播放结果。

模式需要明确选择：`frame_images` 中分别指定 `first_frame` 和 `last_frame`，适用于前后造型的首尾帧控制；`input_references` 适用于角色／动作／风格参考，具体媒体类型以该模型能力为准。官方说明两者同时存在时 `frame_images` 优先，不能假定同时传入就能获得精确首尾帧加动作迁移。参考视频能够引导生成，也不等于逐帧复制动作或保证手指与节拍准确。

OpenRouter 密钥与直接调用 OpenAI 的密钥分别保存在服务端，不能混用；当前设置的基础地址只是占位，不会因为填了 OpenRouter 地址就接通这些端点。

## OpenAI：匹配 hashtags 与自动生成文案

可以在成片生成后，将成片关键帧、视频内容说明、角色设定、发布平台、地区和语言交给支持图像输入的 Responses API，生成 2–3 版短文案与 3–5 个相关 hashtags。多个图像可放在同一个请求里，见 [OpenAI 图像输入说明](https://developers.openai.com/api/docs/guides/images-vision)。抽帧分析只覆盖提供的画面，不能代替整段动作或节拍检查。

“实时匹配”还需要独立的趋势输入：由 Work 或可用的数据服务取得目标平台／地区近期的标签、示例视频、来源 URL 和实际观察时间，再让模型按内容相关度筛选。可以配合 [OpenAI Web search](https://developers.openai.com/api/docs/guides/tools-web-search) 补充带来源的信息；这不等于获得 TikTok／抖音全站实时热榜，也不保证某个标签能增加播放量。两个平台的趋势数据不能混用。

建议把候选标签拆成三类：

- 内容标签：成片实际包含的角色、舞蹈、妆容或造型。
- 趋势标签：近期来源支持、平台和地区相符，并且确实适合这条成片的挑战／歌曲／玩法。
- 品牌标签：用户指定的角色与品牌标签。

每个趋势标签保留来源和观察时间；缺少近期依据时只称“相关标签建议”，不标为“当前热门”。文案必须以实际成片为准，不能照搬参考创作者的身份、宣传内容或无关标签。生成结果先成为草稿，确认后再发布。

现有 `scripts/analyze_tiktok_candidates.py` 只整理候选的文字资料，不看成片、不联网找实时标签，也不生成发布文案。本次未把它伪装成上述功能。后续新增独立的发布草稿服务，密钥存服务端环境变量；公开的 GitHub Pages 只展示数据，不持有密钥或直接调用付费接口。自有角色照片与待发布成片也不放入公开仓库。

## 1. 趋势数据源

实现 `adapters.py` 中的 `TrendProvider.discover(region, category)`，返回与 `/api/state` 中 trends 一致的结构。真实接入时新增并保存来源 URL、观察时间、数据覆盖范围与两次指标快照。不能把样本候选称为全站实时排名。

参考视频仅用于抽象拆解。未授权参考片不进入成片，也不传给生成供应商。第三方趋势接口的使用权限、商业条款与时效需要单独验证。

## 2. 自有素材库

`AssetProvider.list_owned()` 是素材源接口预留。现版本的本地素材由 Store 直接管理，不通过这个占位协议调用外部库。若后续接飞书、Drive、NAS 或对象存储，应仅访问指定素材范围，保留权属与审核状态。共享网页链接不是模型可读取的媒体直链。

可增加 ffprobe 提取时长、编码、画幅与音轨，并在确认素材传输范围后引入可审核的视觉标签。注意代码的 `aspect_ratio` 当前只是人工填写值。

## 3. Seedance 2.5

实现 `GenerationProvider.submit(plan)` 和 `status(remote_id)`，之后再加入结果下载、重试、持久队列、费用与时长校验。当前 `DisabledGenerationProvider` 始终抛出“未接入”错误，防止把模拟误当成实际生成。

在服务端环境变量或正式密钥管理中读取凭据。选择火山方舟或 BytePlus 后，按该账户最新官方文档核对模型 ID、输入格式、时长/画幅限制、真人限制、保存规则、价格与异步状态。不要混用不同供应商的账号和模型 ID。

预留的 API Base URL 字段不会自动被 submit 调用。工程中没有任何伪装成真实调用的“万能端点”。接入前需把实际请求与响应适配器写好并单独测试。

真实调用前至少落实：

- 哪些自有素材可以传到哪个供应商。
- 单条和每日预算，包括失败重试与不满意结果成本。
- 每条补镜的实际模型最小时长与裁剪规则。分镜缺口秒数不等于计费秒数。
- 幂等提交、超时恢复、任务查询、结果文件验证。
- 自有素材比例、模型输入许可、人工审核硬性条件。

## 4. 合成、审核与发布

现在的预演是浏览器逐段播放，不产生合成文件。以后应独立实现 Renderer：使用有权使用的素材与生成片段进行转场、字幕和音轨合成，输出真实文件与来源清单，并检测实际时长和编码。

本地“批准计划”仅改变审核状态。不能把这个动作暗中接到发布。生产版应区分计划批准、允许花费/传输、成片审核和明确发布权限。此版本没有发布接口。

## 5. 不变的本地 HTTP 接口

网页仅通过同源 `/api/*` 与 Python 服务通信。实际请求/响应详见 `API.md`，建议保持前端契约稳定，把供应商差异封装在服务端。API 需增加真实执行阶段与错误类型后再开放生产模式，不能只把 `is_simulation` 设为 false。
